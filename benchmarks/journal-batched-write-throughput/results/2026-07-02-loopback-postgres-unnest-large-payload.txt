Journal write throughput and stability for very large events: default vs add() vs UNNEST
========================================================================================

Extends the payload-size study beyond 128 KB (including non-power-of-2 sizes) to find where
each strategy breaks down. The headline finding is a *stability* one, not just throughput:
the UNNEST path runs out of memory and fails for large events, while default and add()
survive.

Environment
-----------
PostgreSQL 18.4 over loopback (docker, port 5433), JDK 17.0.19 (temurin), Scala 2.13,
12-CPU host (62 GB RAM). Forked test JVM at -Xmx6g (default MaxDirectMemorySize = 256 MB).
Pool max-size=20, batched defaults (batch.window=10ms, batch.max-requests=100,
batch.parallelism=8). actorCount=500 (size-flush regime), eventsCount=5, warmup=1, best of
2. event_journal TRUNCATEd between sizes. Payload is a fixed-size byte array per event
(pekko.bench.payloadSize; PayloadBenchActor). All three journals in the same session.

NOTE: eventsCount=5 / iterations=2 makes the absolute default-vs-add() numbers noisy at
these sizes (I/O-bound, high variance - see the 300 KB default outlier). The robust,
repeatable finding is the UNNEST OutOfMemoryError at >= 256 KB.

Findings
--------
1. UNNEST is a hard liability for large events - it FAILS, not just slows. At >= 256 KB it
   throws OutOfMemoryError (direct buffer memory, then Java heap at 512 KB). Cause: the
   UNNEST insert hex-encodes each payload (2x) and materializes the whole coalesced batch
   as one statement's array parameters in off-heap Netty buffers; a batch of up to
   batch.max-requests rows * 2 * payloadSize easily exceeds the 256 MB direct-memory limit.
   Raising -Xmx does not help (direct memory is off-heap); at 512 KB it also exhausts heap.
2. default and add() survive all sizes: default writes single rows; add() streams per-row
   bind parameters; neither hex-encodes. So neither materializes a giant buffer.
3. Even where UNNEST completes (128-150 KB) it is ~2x slower than default/add().
4. default vs add() for large events: default is generally >= add() and add() collapses at
   the top (512 KB: add() 254 vs default 530). Batching very large payloads into one
   transaction inflates transaction size/latency more than it saves, so *not batching* is
   best. (Absolute numbers are noisy here; the ordering default >= add() >> UNNEST-or-OOM is
   the takeaway.)

Implications
------------
- Do NOT enable batch.use-unnest for workloads with large events (>= a couple hundred KB is
  an outright OOM risk with default batch sizes; the memory needed scales with
  batch.max-requests * 2 * payloadSize of off-heap buffer). This is a correctness/stability
  concern, not only performance.
- The current codec guard (bytea vs json) is not sufficient protection. A future auto-select
  heuristic (or a hard payload-size cap) should restrict UNNEST to small events and fall
  back to add() otherwise - now motivated by stability, not just throughput.
- A bytea[] binding (if the driver gains support) would remove the hex 2x and reduce, though
  not eliminate, the large-batch memory pressure.

"When to use what" across the full size range (high concurrency, loopback)
--------------------------------------------------------------------------
  <= ~8 KB          : UNNEST   (fastest)
  ~8 KB .. ~150 KB  : add()    (UNNEST fading/at 2x slower; still completes)
  >= ~256 KB        : default  (no batching; UNNEST OOMs, add() drops below default)
